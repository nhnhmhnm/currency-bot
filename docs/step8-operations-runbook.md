# 8번 운영 전환·복구 체크리스트

이 문서는 실행 기록이 아니다. 기존 `cuunit` 데이터베이스 전환은 보류 중이며, 아래 절차와 SQL을 적용하지 않았다.

## 전환 전 차단 조건

1. 접수 API와 모든 Worker를 중지하고, MySQL 백업을 별도 스키마에 복원해 무결성을 확인한다. Redis Stream/List의 pending 수와 DB 미완료 주문·Outbox 수를 함께 기록한다.
2. 기존 지갑 `(user_id, currency_id)`, 연결계좌 `(bank_id, account_num)` 중복, 음수 잔액, 종료 주문의 활성 예약, 완료 주문의 전표·체결 누락을 조회한다. 발견 항목은 건별 원인을 확정하고 수정 승인·증적을 남긴다.
3. 기존 `account.balance`는 외부 은행 잔액으로 간주해 자동 이관하지 않는다. `internal_account` 회사 현금·수수료 기초 금액은 실제 보유 자산과 고객 채무 대사 후 담당자 승인으로 확정한다. 과거 요약 기록에서 상세 분개를 추측해 생성하지 않는다.
4. 1~4번 변경의 기존 DB용 기준선 DDL·데이터 이관·롤백 절차가 아직 없다. 이것이 준비되기 전에는 5~8번 SQL만 실행하거나 새 애플리케이션을 `cuunit`에 연결하지 않는다. 운영에서는 Hibernate `ddl-auto=update`에 스키마 변경을 맡기지 않고 검증 모드를 사용한다.

## 격리 리허설과 전환

1. 복원한 격리 스키마에서 기준선 이관을 검증한 뒤 [5번](../backend/scripts/migrations/step5-arbitrage-four-slots.sql), [6번](../backend/scripts/migrations/step6-journal.sql), [7번](../backend/scripts/migrations/step7-completed-order-view.sql), [8번](../backend/scripts/migrations/step8-order-recovery-audit.sql) DDL을 순서대로 적용한다. 각 단계에서 제약·자릿수·행 수와 잔액을 비교한다.
2. 기존 List 메시지를 소진하고 주문 상태·예약·접수 Outbox를 대조한다. List 키를 삭제해 전환하지 않는다. Streams Worker는 기존 접수 주문의 DB 복구 경로가 준비된 뒤 기동한다.
3. 기초 잔액 기준점을 보관하고 신규 전표 이후 구간부터 대사를 수행한다. 완료 조회 모델은 완료 Outbox로 재생성하며 자금 원장으로 사용하지 않는다.
4. 소액 모의 입금→환전→출금, 중복 요청, ACK 누락, 완료 이벤트 유실을 검증한다. 회사 현금·고객 지갑·분개·예약·미완료 주문 수가 일치할 때만 접수를 재개한다.

## 장애와 수동 복구

- Redis 장애 후에는 Outbox와 DB 미완료 주문을 기준으로 재발행한다. 중복 전달은 예상 가능한 상태이며 주문 잠금·종료 상태·전표 유니크 제약으로 자금 이중 반영을 막는다.
- `POST /api/admin/orders/{orderId}/requeue`는 `SUPER` 권한과 3~500자 사유가 필요하다. 명령 결과와 행위자 ID는 `order_recovery_audit`에 남긴다. 종료 주문이나 활성 예약이 없는 주문은 재정산하지 않는다. 재발행은 처리 완료가 아니라 새 Outbox 접수다.
- `GET /api/admin/exchange/operations`는 미완료 주문·미발행 Outbox의 수와 최고 경과 시간, 현재 애플리케이션 프로세스의 정산 잠금 획득 호출 횟수·평균·최대를 보여준다. 잠금 수치는 DB 조회·네트워크 시간을 포함하는 근사치이고 재시작 시 초기화되며 외부 수집·경보를 대체하지 않는다.
- 외부 은행 요청은 현재 없다. 현재 모의 은행 잔액은 같은 DB 트랜잭션 안에서만 변경된다. 실제 은행을 붙일 때는 요청 ID, 별도 이체 상태, 출금 예약, 결과 조회·대사, 결과 불명 상태를 구현해야 한다. 응답 타임아웃을 실패 확정하거나 예약 해제로 처리하면 안 된다.

## 별도 비동기 은행 이체 설계 (미구현)

기존 `/api/wallet/deposit`·`withdraw`는 로컬 모의 API로 유지한다. 신규 흐름은 별도 경로에서만 제공하고, 아래 계약과 검증을 갖추기 전에는 활성화하지 않는다.

1. 인증 사용자·계좌 소유권·금액·통화를 검사한다. 클라이언트 요청 키와 요청 내용 해시를 유니크하게 저장하고 은행 요청 ID를 확정한 뒤, 이체 요청과 발행 Outbox를 한 DB 트랜잭션으로 접수한다. 동일 키·동일 내용은 같은 요청을 반환하고 다른 내용은 거절한다.
2. 출금은 사용자→지갑 잠금 아래 가용 잔액을 확인해 별도 예약을 만든다. 이 예약을 환전 접수와 다른 출금의 가용 잔액 계산에도 포함한다. 입금은 은행 확정 전 고객 지갑이나 회사 현금을 늘리지 않는다.
3. Worker는 은행 요청 ID로 한 번 제출하거나 같은 ID의 결과를 조회한다. `접수 → 제출 → 결과 불명/확정 성공/확정 거절 → 내부 반영 완료`를 구분한다. 타임아웃은 결과 불명으로 두고 새 ID로 재송금하지 않는다. 확정 거절 때만 출금 예약을 해제한다.
4. 은행 성공을 확인하면 별도 DB 트랜잭션에서 지갑·회사 현금·입출금 원본·전표·예약 해제/소비·완료 상태를 함께 확정한다. 내부 기장 실패 시 은행을 재호출하지 않고 동일 요청 ID의 확정 결과를 근거로 내부 기장만 재시도한다. 은행 성공 후 내부 장부가 미완료인 건은 대사에서 반드시 탐지한다.
5. 사용자 조회는 처리 중/완료/거절만 보여주고 내부 장애 세부 정보는 숨긴다. 운영 대사는 은행 결과, 요청 상태, 예약, 입출금 원본, 전표를 요청 ID별로 비교한다. 결과 불명 장기 체류와 승인된 수동 조치는 별도 감사 대상이다.

현재 모의 은행 잔액은 애플리케이션과 같은 MySQL 트랜잭션에 있으므로 이 설계의 은행 성공 후 응답 타임아웃을 재현하지 못한다. 이를 테스트하려면 독립 커밋되는 은행 시뮬레이터 또는 별도 서비스가 필요하다.

## 중단·롤백 판단

- 스키마 또는 대사가 맞지 않으면 접수를 재개하지 않는다. 배포 전 백업은 정지 상태 복구용이다. 신규 거래가 발생한 뒤 단순 DB 복원이나 신규 전표 삭제로 되돌리지 않는다.
- 새 버전을 중지해도 신규 Stream pending·Outbox·전표를 보존한다. 이전 버전으로 복귀할 때는 이전 코드가 새 스키마와 주문 상태를 해석할 수 있는지 격리 리허설로 확인한다. 불가능하면 이전 바이너리를 가동하지 않고 전진 수정한다.
- 전환 증적에는 백업 복원 결과, 시작·종료 잔액, 주문/예약/Outbox 수, 전표 대사 결과, 테스트 로그, 승인자와 시각을 남긴다.
