# 환전 백엔드 리팩토링 계획

목표: 입금·환전·출금을 정확하게 처리하고, 중복 요청이나 장애가 발생해도 자금과 기록을 복구할 수 있게 한다.

상태: 1~7번의 신규 데이터 경로를 구현하고 H2·mock 및 격리된 MySQL·Redis에서 검증했다. 기존 DB 이관과 8번은 계획이다. 실제 프로세스 강제 종료·Redis 재시작·운영 스키마 전환은 아직 검증하지 않았다. 각 항목 구현 후 테스트 결과·측정값·커밋을 기록한다. 기대 효과를 완료 실적으로 표시하지 않는다.

## 1. 일반 입출금 검증과 계좌 접근 통제

- **현재 문제:** 일반 입출금은 양수 금액 검증과 잠금 없이 잔액을 직접 변경한다. 계좌 생성 API는 비인증 접근을 허용하며 요청 userId와 초기 잔액 10억 원을 사용한다.
- **개선·근거:** 금액·통화·계좌 상태·소유권을 검사하고 모든 자금 변경에 공통 잠금 규칙을 적용한다. 계좌 생성은 권한을 확인하고 테스트 자금은 개발용 seed로 격리한다. 환전 경로만 보호하면 일반 출금을 통한 정합성 훼손이 남는다.
- **결과 검증:** 음수 입출금과 무권한 계좌 생성을 거절하고, 환전·출금 동시 실행에서도 갱신 유실과 음수 가용 잔액이 없어야 한다.
- **코드 근거:** [WalletServiceImpl](../backend/src/main/kotlin/org/example/backend/user/service/WalletServiceImpl.kt), [SecurityConfig](../backend/src/main/kotlin/org/example/backend/common/config/SecurityConfig.kt), [AccountServiceImpl](../backend/src/main/kotlin/org/example/backend/user/service/AccountServiceImpl.kt).
- **실제 결과 (H2):** 비인증 계좌 생성 거절, 인증 사용자 명의·초기 잔액 0 생성, 양수/통화 자릿수·연결 계좌 소유권/활성/통화 검사, 사용자→지갑→계좌 잠금 및 활성 주문 예약액을 반영한 출금을 구현했다. 기존의 의미 없는 회사 계좌 왕복 변경은 제거했다. 테스트 자금은 통합 테스트 fixture에만 넣었다. 구현 커밋 `0354955`. `backend/gradlew.bat test --no-daemon` 전체 58개 통과(2026-10-13). 실제 은행 잔액 검증·MySQL 잠금과 회사 자산/고객 채무 회계 처리는 3·4·8번 범위로 남는다.
- **추가 검증 (MySQL 9.4):** `REPEATABLE-READ`에서 통화 조회가 사용자 잠금보다 앞서면 오래된 예약액·일일 한도를 읽어 초과 주문이 접수되는 결함을 발견했다. 주문 접수와 입출금에서 사용자 잠금을 첫 DB 조회로 이동한 뒤 동시 주문 11건, 일일 한도 경합 6건, 주문·출금 경합 테스트가 통과했다. 실제 은행 잔액이 아닌 로컬 모의 잔액 검증이며 잠금 순서 전체의 데드락·부하 검증은 4·8번에서 계속한다.

## 2. Worker 실패 처리와 중복 실행 방지

- **현재 문제:** ACK 오류를 정산 실패로 취급한다. 최종 재시도에서는 메시지 제거 후 DB에 실패를 기록하므로 중간 장애 시 주문이 미완료로 남을 수 있다. lease 복구에는 소유권 경합 위험도 있다.
- **개선·근거:** 정산과 ACK 예외를 분리하고, 최종 실패·예약 해제를 DB에 확정한 뒤 ACK한다. 재시도 횟수·다음 실행 시각을 DB에 보존하고 지연 재시도·격리·미완료 주문 복구를 제공한다. 기존 List 유지 중에는 claim 소유권을 원자적으로 검사한다.
- **멱등성:** 기존 사용자·요청 키 제약을 유지하고 키 필수화 전환을 준비한다. 동일 키·다른 내용은 거절한다. 재전달은 주문 잠금·종료 상태 확인과 정산 전표 유니크 제약으로 보호한다. Redis 중복 방지 키 만료에 자금 안전성을 맡기지 않는다.
- **결과 검증:** 커밋 전후 Worker 종료, ACK 실패, 실패 기록 저장 실패, 중복 전달에도 자금은 한 번만 반영되고 접수 주문을 추적·복구할 수 있어야 한다.
- **코드 근거:** [OrderWorker](../backend/src/main/kotlin/org/example/backend/exchange/service/OrderWorker.kt), [RedisOrderQueue](../backend/src/main/kotlin/org/example/backend/common/util/RedisOrderQueue.kt).
- **실제 결과 (H2·mock):** 구현 커밋 `a31990e`. 정산 실패만 DB에 재시도 횟수·다음 시각(최대 3회, 2/4초 지연) 또는 최종 FAILED를 확정한 후 Redis 메시지를 이동한다. ACK 실패는 재정산 실패로 세지 않는다. List claim의 lease 소유권 확인, 지연 큐, 만료 lease 복구, 60초 이상 미완료 주문의 DB 기준 재발행을 추가했다. 동일 주문 동시 전달·늦은 실패 보고·재시도 중복 보고 등을 포함해 `backend/gradlew.bat test --no-daemon --rerun-tasks` 전체 66개 통과(2026-10-13). 실제 Redis Lua/Worker 강제 종료 및 MySQL 잠금은 미검증이다. 전표 유니크 제약은 6번, Streams 전환은 7번, 운영 스키마 마이그레이션은 8번에서 검증한다.
- **추가 검증 (MySQL·Redis):** 실제 Redis에서 Lua claim·lease 소유권·오래된 ACK 거절·지연 재시도와 Worker 중복 전달을 확인했다. claim 후 미정산 상태와 DB 정산 커밋 후 ACK 전 상태를 Redis에 재현해 복구 후 자금·거래 기록이 한 번만 반영됨을 확인했다. [실행 스크립트](../backend/scripts/verify-local-infra.ps1)는 전용 `currency_bot_integration_test` 스키마와 비어 있는 Redis DB 15만 사용한다. OS 프로세스 강제 종료·Redis 재시작·전표 유니크 제약(6번)·Streams pending(7번)은 아직 검증하지 않았다.

## 3. 지갑·외부 계좌·회계계정 구분

- **현재 문제:** Account가 사용자 연결계좌와 회사 계좌 역할을 함께 담당한다. Wallet에는 연결 상태가 중복 표현되며, 잔액 정밀도와 사용자·통화 유니크 제약은 실제 DB 확인이 필요하다.
- **개선·근거:** 지갑은 고객의 통화별 채무 잔액, 연결계좌는 외부 은행 참조, 내부 계정은 회사 현금 자산·수수료 수익으로 구분한다. 고객 채무의 정식 분개계정은 6번에서 추가한다. 잔액의 기준을 하나로 정하고 정밀도·유니크 제약을 명시한다. 외부 은행 잔액을 로컬 값 변경만으로 실제 이체했다고 취급하지 않는다.
- **결과 검증:** 입금·환전·출금의 회사 자산과 고객 지갑 변동을 설명할 수 있어야 한다. 지갑을 회사의 고객 채무로 정의하면 입금 시 회사 예금 자산과 고객 지갑 채무가 함께 증가하며, 이는 자금 중복 지급이 아니다.
- **코드 근거:** [Wallet](../backend/src/main/kotlin/org/example/backend/user/domain/Wallet.kt), [Account](../backend/src/main/kotlin/org/example/backend/user/domain/Account.kt).
- **실제 결과 (H2·mock):** 구현 커밋 `91e4eb5`. `Account`는 외부 계좌 참조만 보관하고, 로컬 모의 잔액은 `SimulatedBankBalance`, 회사 통화별 현금·수수료 수익은 `InternalAccount`로 분리했다. `Wallet.accountId`만 연결 기준으로 사용하고 지갑·계좌 유니크 제약과 잔액 `DECIMAL(24,8)`을 명시했다. 입금은 모의 은행 잔액 감소/회사 현금·지갑 증가, 출금은 역방향, 환전은 회사 통화별 현금 교환/고객 지갑 변동/수수료 수익을 같은 DB 트랜잭션에 반영한다. 모의 입출금은 `APP_BANK_SIMULATION_ENABLED=true`인 환경에서만 허용하며 기본값은 비활성이다. 실제 은행 이체·체결 연동은 없다. BUY/SELL·중복 정산·롤백·회사 유동성 부족·입출금 차단·DB 유니크 제약을 포함한 `backend/gradlew.bat test --no-daemon --rerun-tasks` 전체 70개가 통과했다(2026-10-13). 기존 DB의 회사 잔액과 외부 계좌 데이터를 자동 이관하지 않으며, 중복 데이터 정리·초기 내부 계정 적재·실제 MySQL 제약 확인은 8번 배포 절차에서 수행해야 한다. 고객 채무 집계와 복식 분개는 6번, 전역 잠금 순서와 PostingPlan은 4번에 남는다.
- **추가 검증 (2026-10-13):** 격리된 MySQL 9.4·Redis에서 20개 통과, 전체 H2·mock에서 71개 통과·실환경 전용 4개 건너뜀. 입금→BUY→SELL→출금의 단계마다 `회사 KRW 현금 변화 = 사용자 KRW 지갑 변화 + 수수료 수익 변화`, `회사 USD 현금 변화 = 사용자 USD 지갑 변화`와 모의 은행 잔액 변화를 대조했다. 새 MySQL 스키마의 세 잔액 컬럼은 `DECIMAL(24,8) NOT NULL`, 지갑·외부 계좌·내부 계정·모의 은행 잔액 중복 삽입은 DB가 거절함을 확인했다. 테스트 후 전용 스키마와 Redis DB 15는 비어 있다.
- **기존 DB 전환 미완료:** 기존 개발용 `cuunit` 스키마는 읽기 전용으로 확인했다. 지갑 9건·계좌 7건에 대상 유니크 키 중복 그룹은 없지만, 두 잔액은 여전히 `DECIMAL(38,2)`이고 `wallet.is_connected`·`account.balance`가 남아 있으며 `internal_account`·`simulated_bank_balance` 테이블이 없다. 새 스키마 테스트 통과가 데이터 이관 완료를 뜻하지 않는다. 8번에서 백업·잔액 대사·내부 계정 초기값 확정·단계적 DDL·롤백 절차를 준비한다. 실제 은행 연동과 정식 고객 채무 분개도 아직 없다.

## 4. 정산 실행기와 잠금 규칙 통합

- **현재 문제:** BUY·SELL에서 이체 호출을 나열하고 개별 이체마다 출금 측부터 잠근다. 반대 방향 거래 간 잠금 순서가 충돌할 수 있으며 접수 검증을 우회하는 즉시 처리 경로도 있다.
- **개선·근거:** 금액·수수료를 계산하는 PostingPlan과 실제 기장하는 PostingService를 분리한다. 정산은 주문 행→사용자→통화 ID순 지갑→코드순 내부 계정을 잠근다. 접수·입출금은 사용자→지갑을 먼저 잠그고 입출금만 외부 계좌→내부 계정→모의 은행 잔액을 잇는다. 동일 사용자 경합은 사용자 잠금으로 직렬화하고, 회사 공유 계정은 고정 순서로 잠근다. 교착 예외는 Worker가 정산 트랜잭션 전체를 새 시도에서 재실행한다.
- **원자적 범위:** 현재 잔액, 지갑 이력, 거래 원본, 환전 요약 장부, 주문 완료, 완료 Outbox를 한 DB 트랜잭션으로 저장한다. 주문 내부의 출금·입금을 병렬화하지 않는다. 차익거래는 부모만 접수·예약하고 하위 체결은 같은 정산 트랜잭션에서 실행한다. 명시적 예약 행은 5번, 정식 전표·분개는 6번 범위다.
- **결과 검증:** 어떤 중간 단계에서 예외가 나도 정산 변경이 모두 롤백되어야 한다. 공통 계산 결과만 공유하고 주문·체결·전표 DTO는 책임별로 유지한다.
- **코드 근거:** [ExchangeOrderServiceImpl](../backend/src/main/kotlin/org/example/backend/exchange/service/ExchangeOrderServiceImpl.kt), [PostingPlan](../backend/src/main/kotlin/org/example/backend/exchange/service/PostingPlan.kt), [PostingService](../backend/src/main/kotlin/org/example/backend/exchange/service/PostingService.kt).
- **실제 결과 (2026-10-14):** BUY·SELL의 다중 이체 호출과 공개 즉시 체결 경로를 제거했다. PostingPlan은 통화별 `회사 현금 변화 = 고객 지갑 변화 + 수수료 수익 변화`를 검사하고, PostingService는 모든 대상 행을 잠근 후 한 트랜잭션에서 기장한다. 정상 완료 Outbox는 주문별로 저장하며 차익거래 하위 주문은 별도 완료 이벤트를 만들지 않는다. 회사 현금 부족·장부 기록 실패 시 이력·잔액·거래·완료 이벤트까지 롤백되고, 서로 다른 사용자 BUY/SELL 동시 정산과 중복 전달이 격리된 MySQL·Redis 테스트에서 통과했다. 완료 이벤트 발행·후처리는 7번에서 구현한다.
- **추가 검증 (2026-10-14):** 테스트에서만 KRW·USD 회사 계정을 역순 선잠금해 실제 BUY·SELL 정산 간 InnoDB 교착(`SQLSTATE 40001`, 오류 1213)을 재현했다. 피해 주문은 접수 상태로 롤백되고 거래·장부·완료 이벤트가 생기지 않았으며, 접수 Outbox의 Redis 재전달 후 두 주문이 각각 한 번만 정산됐다. Worker가 직접 1213을 받아 지연 재시도를 계획하는 경로는 별도 모의 예외 테스트로 검증했다. `verify-local-infra.ps1 -IncludeLoadBaseline`의 로컬 단일 Worker 20명·100건 동시 접수 버스트 2회에서 접수 671~802ms, 큐 발행 363~448ms, 정산 5.11~5.20초(19.23~19.55건/초), 접수→완료 p95 5.34~5.57초였다. 100건 모두 오류·중복·잔액 불일치가 없었다. HTTP 계층, 지속 도착률, 다중 Worker, 부하 한계와 실제 은행 연동은 측정하지 않았다.

## 5. 접수 시 자금 예약과 견적 확정

- **현재 문제:** 활성 주문의 자금 점유를 일반 출금과 공유하지 않았고, 접수·정산 사이 환율 변화의 처리 근거가 부족했다.
- **개선·근거:** 접수 트랜잭션에 주문·자금 예약·동의 견적·Outbox를 함께 저장한다. 일반 BUY/SELL에는 프로젝트 일일 USD 한도를 두지 않는다. 차익거래는 통화 공통으로 서울 날짜당 완료 4회, 회당 정확히 1,000,000 KRW다. 접수 중인 주문도 4개 슬롯을 점유하고 취소·최종 실패 시 반환한다. 사용자 잠금과 DB 유니크 제약으로 동시 접수를 제한한다. 모든 출금은 `잔액 - 활성 예약액`만 사용한다.
- **견적·상태:** 차익거래 예상 순수익은 KRW→FX 절사, FX→KRW 절사, 최종 KRW 수수료 0.003% 1회 올림 후 계산해 주문 전에 보여준다. 음수 견적은 접수하지 않는다. 접수 전 잔액·한도 거절은 주문 이력에 남기지 않는다. 동의한 환율이 접수 전 달라지면 거절하고 정산 전 달라지면 `RATE_CHANGED` 취소와 예약 해제를 한다. 기타 최종 실패는 사용자에게 일반화하고 내부 오류는 별도 보관한다.
- **결과 검증:** 잔액 예약·일반 출금·재처리·실패 롤백, USD/JPY 공통 슬롯 4회, 수수료 반영 손익 및 USD 고시 없는 JPY 견적을 테스트한다. 4,000 USD는 모든 환전에 공통 적용되는 법정 한도로 가정하지 않는다. 관세청의 등록 환전영업자 외화 매각 한도와 은행 환전 상품 규칙은 구분한다([관세청 안내](https://www.customs.go.kr/kcs/na/ntt/selectNttInfo.do?bbsId=1362&mi=2891&nttSn=10169304&nttSnUrl=fb0d3435b97db1b90771d20d24e1f1cf)).
- **실제 결과 (2026-10-14):** 구현 커밋 `eec0492`. 일반 환전의 일일 USD 환산 의존성을 제거하고, 차익거래 100만 원 고정·서울 날짜당 4개 슬롯·자금 예약·동의 견적 및 순수익 표시를 적용했다. USD/JPY 혼합 4회, 취소 슬롯 재사용, 수수료·절사 손익분기, 주문자 전용 상태 조회와 환율 변경 취소 알림을 H2 및 격리된 MySQL·Redis에서 검증했다. 전체 백엔드 테스트·프론트 단위 테스트·빌드가 통과했고, 모바일·데스크톱 주문 E2E가 통과했다. 차트 E2E는 8개 브라우저 병렬 실행에서 1회 타임아웃이 있었으나 단독 재실행에서 통과했다. 실환경 테스트 후 전용 MySQL 스키마와 Redis DB 15는 비어 있었다.
- **배포·남은 일:** 기존 DB에 1일 1회 유니크 제약이 있으면 [5번 스키마 전환 SQL](../backend/scripts/migrations/step5-arbitrage-four-slots.sql)을 백업·점검 후 적용한다. 실은행의 체결 가능 호가·외부 비용은 이 모의 시스템에 없으므로 예상 수익 보장이 아니다. 견적 만료 시간·일부 환율 변동 허용 여부, 기존 주문 데이터 이관은 8번 배포 절차에서 결정한다.

## 6. 전표·분개와 대사 도입

- **현재 문제:** 장부가 환전 요약 중심이어서 주문별 계정 증감과 현재 잔액을 충분히 대사하기 어렵다.
- **개선·근거:** 주문에 연결된 전표와 계정·통화별 차대 분개를 저장하고 통화별 차변·대변 합계를 검증한다. 정산 단위의 유니크 제약을 두며, 확정 전표는 수정 대신 역분개로 정정한다. 원장은 변경 근거, 잔액은 같은 트랜잭션에서 유지되는 운영 집계값으로 관리한다.
- **결과 검증:** 기초 잔액과 분개로 기말 잔액을 설명하고, 성공 주문의 전표 누락·중복·예약 잔류를 배치로 탐지해야 한다. 주문 하나에 분개가 여러 행이므로 단순 행 수 동일 비교는 하지 않는다.
- **코드 근거:** [ExchangeLedger](../backend/src/main/kotlin/org/example/backend/exchange/domain/ExchangeLedger.kt).
- **실제 결과 (2026-10-14):** 환전 체결별 전표와 입출금별 전표를 잔액 변경과 같은 트랜잭션에 저장한다. 고객 지갑은 채무, 회사 현금은 자산, 수수료는 수익 계정으로 기장하며 통화별 차대 합계와 계정별 기장 전후 잔액을 검사한다. 차익거래는 부모가 아니라 두 하위 체결에 각 전표를 둔다. 전표 원천 유형·ID 유니크 제약으로 중복 정산 전표를 거절하고, 후속 거래 기록 실패 시 전표·분개·잔액을 함께 롤백한다. 대사는 성공 체결/입출금의 전표 누락, 차대 불일치, 기장 연속성·실제 잔액 차이, 종료 주문의 예약 잔류를 탐지한다. 배치는 `app.accounting.reconciliation-enabled=true`일 때만 실행한다. H2 전체 테스트 96개 중 90개 실행·6개 건너뜀·실패 0개, 격리된 MySQL·Redis 통합 테스트 통과. [전표 코드](../backend/src/main/kotlin/org/example/backend/finance/service/JournalService.kt), [대사 코드](../backend/src/main/kotlin/org/example/backend/finance/service/JournalReconciliationService.kt).
- **배포·한계:** 기존 DB에는 [6번 DDL](../backend/scripts/migrations/step6-journal.sql)을 백업·점검 후 적용한다. 과거 거래 요약에서 상세 분개를 임의 생성하지 않는다. 계정별 첫 신규 분개의 `balanceBefore`를 기초 잔액으로 삼으므로 기존 잔액·과거 주문은 운영 전환 시 별도 기준점 대사가 필요하다. 전표는 수정하지 않으며 실제 정정은 승인·사유·역분개·원주문 표시를 포함하는 통제된 보정 거래로만 수행해야 한다. 현재 보정 API와 역사 데이터 이관은 제공하지 않는다. 전체 테이블을 읽는 대사 배치는 운영 데이터 규모에 맞춰 페이지/증분 방식으로 확장한 뒤 활성화한다.

## 7. 정산 큐와 후처리 분리

- **현재 문제:** 직접 구현한 List·lease 복구 구조이며 Outbox는 접수 이벤트 중심이다. 큐 수를 늘리는 것만으로 순서·유실·중복 문제가 해결되지는 않는다.
- **개선·근거:** Redis Streams의 pending·인계·ACK를 사용하되 DB 멱등성과 미완료 주문 복구를 유지한다. Outbox의 발행 완료는 업무 완료가 아니므로 Redis 유실 시에도 DB에서 재발행할 수 있어야 한다.
- **분리 범위:** 우선 정산과 후처리 실행 자원을 분리한다. 자금·전표·체결 원본은 동기 저장하고 재생성 가능한 조회 데이터·알림·통계만 완료 이벤트로 처리한다. 여러 기능이 모두 이벤트를 받아야 하면 독립 구독을 사용한다.
- **순서 정책:** 초기 단일 Worker에서 시작하고 동일 사용자 순서 보장이 필요하면 DB 접수 순번과 선행 주문 확정 검사를 적용한다. 다중 Worker는 다른 사용자 주문부터 병렬화하되 회사 공용 계좌 경합을 측정한다.
- **결과 검증:** 후처리 장애가 정산 완료를 되돌리지 않고, 중복·역순 이벤트에도 조회 결과가 일치해야 한다. 미완료 주문 나이·Outbox 지연·락 대기를 측정한다. [Outbox 코드](../backend/src/main/kotlin/org/example/backend/exchange/service/OutboxEventPublisher.kt).
- **실제 결과 (2026-10-14, 구현 커밋 `20892ae`):** 정산 List/수동 lease를 Redis Stream consumer group의 pending·claim·ACK로 교체했다. DB의 주문 상태·재시도·60초 이상 미완료 주문 재발행을 유지해 Redis 전달 보장만으로 자금 안전성을 판단하지 않는다. 완료 Outbox는 별도 Stream/Worker가 소비하여 사용자별 완료 주문 조회 모델을 만들며, 자금·전표·체결 원본·주문 완료는 기존 단일 DB 정산 트랜잭션에 남는다. 조회 모델은 주문 ID와 이벤트 ID 유니크 제약으로 중복 반영을 막고, 완료 Outbox 전수 검사로 Redis 유실 후 재발행할 수 있다. H2에서 후처리 실패/역순·중복 이벤트와 사용자별 조회를, 격리된 MySQL·Redis에서 pending 인계/오래된 ACK 거절/완료 Stream 유실·재발행 및 정산 중복 방지를 확인했다. 전체 백엔드 테스트 103개 중 96개 실행·7개 실환경 전용 건너뜀·실패 0개, 별도 실환경 통합 테스트 37개 중 36개 실행·부하 기준선 1개 건너뜀·실패 0개였다.
- **배포·남은 일:** 기존 `cuunit`에는 [7번 조회 모델 DDL](../backend/scripts/migrations/step7-completed-order-view.sql)을 적용하지 않았다. 운영 전환 시 기존 List를 소진하고 미완료 주문과 Outbox를 대사한 뒤 Stream Worker를 켠다. 조회 모델은 과거 완료 이벤트를 재생해 채우며 자금 데이터의 대체 원장이 아니다. 전체 완료 Outbox를 주기적으로 훑는 복구 배치는 데이터 증가 시 증분/페이지 대사로 바꿔야 한다. 미완료 주문 나이·Outbox 지연·락 대기 지표의 계측, 다중 Worker 처리량, 프로세스 강제 종료·Redis 재시작은 아직 측정하지 않았다.

## 8. 외부 연계와 실제 결과 검증

- **현재 한계:** 로컬 MySQL 잠금·Redis lease·단일 Worker 100건 버스트를 검증했지만 프로세스·Redis 강제 종료, 실제 은행 연동, 운영 스키마 전환과 지속 부하 성능은 입증하지 못했다. 모의 은행 잔액 처리는 실제 은행 연동과 구분해야 한다.
- **개선·근거:** 실제 MySQL·Redis 통합 테스트와 모의 은행을 사용한다. 은행 요청 ID, 결과 조회, 대사를 구현해 은행 성공 후 응답 타임아웃을 재현한다. 외부 결과 불명은 바로 실패 확정하거나 예약 해제하지 않는다.
- **필수 검증:** 단계별 롤백, 잔액 초과 동시 주문, 중복 요청, Worker 강제 종료, 한도·JPY 고시 단위·반올림 경계, 대사 배치 재실행. 수동 재처리는 권한·사유·결과를 감사 기록으로 남긴다.
- **배포 기준:** 스키마를 단계적으로 추가하고 기존 활성 주문·예약·큐를 대사 후 전환한다. 과거 요약으로 상세 분개를 임의 복원하지 않는다. 기존 주문 소진과 롤백 절차를 검증한다.
- **실제 결과 기록:** 수정 커밋 `da7f3a0`, 테스트 커밋 `79c840e` 이후 4번 추가 검증까지 `backend/scripts/verify-local-infra.ps1 -IncludeLoadBaseline`로 MySQL 9.4 (`REPEATABLE-READ`)·Redis 25개 통과, `backend/gradlew.bat test --no-daemon --rerun-tasks`로 H2·mock 76개 통과·실환경 전용 6개 건너뜀(2026-10-14). 테스트 후 전용 MySQL 스키마 테이블 수와 Redis DB 15 키 수는 모두 0이다. 기존 `cuunit` 이관, OS 강제 종료·Redis 재시작·지속 부하 측정은 아직 없다. MSA 확장보다 이 증거를 우선한다.

## 9. 최종 처리 흐름

```text
주문 API: 동일 요청에는 동일 idempotencyKey
  -> [접수 DB 트랜잭션]
     중복 확인·검증 + 자금·한도 예약 + 주문 + 접수 Outbox
  -> COMMIT 후 "접수됨" 응답 (환전 완료 아님)
  -> Outbox 발행 -> 정산 큐 -> Worker
  -> [정산 DB 트랜잭션]
     공통 순서로 잠금 -> 종료 상태·처리 순서·견적·예약 검증
     -> 잔액 반영 + 전표·체결 원본 + 예약 사용
     -> 주문 완료 + 완료 Outbox
  -> COMMIT -> ACK
  -> 완료 이벤트 -> 조회 데이터·알림·통계 후처리

견적 정책 위반: 주문 취소 + 예약 해제 커밋 -> ACK
정산 예외: 전체 롤백 -> 별도 DB 트랜잭션으로 재시도 계획 저장
최종 실패 확정: 종료 상태 재확인 + 실패·예약 해제 커밋 -> ACK
장기 미완료: DB 기준 탐지 -> 재발행 또는 운영 확인
```

이 흐름은 내부 DB 정산 기준이다. 외부 은행 결제가 포함되면 요청·결과 확인·대사를 별도 단계로 두고 고객에게 약속하는 완료 시점을 정의한다. 외부 송금은 DB 롤백으로 되돌릴 수 없다.

참고: [MySQL 잠금·교착](https://dev.mysql.com/doc/refman/8.0/en/innodb-deadlocks.html), [Redis 인계](https://redis.io/docs/latest/commands/xautoclaim/), [Outbox 패턴](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html).
