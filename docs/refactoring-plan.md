# 환전 백엔드 리팩토링 계획

목표: **전체 주문의 순차 실행에 의존하던 구조를, 필요한 순서만 유지하면서 DB 트랜잭션·잠금·멱등성으로 자금 정합성을 보장하는 구조로 바꾼다.** 큐는 실행 전달과 부하 조절, DB는 잔액·예약·정산 결과의 기준을 맡는다.

범위: 우선 단일 애플리케이션·단일 DB에서 내부 정산을 완성한다. 실제 은행 연동은 후속 단계다. 이미 있는 Outbox·주문 멱등키·일부 비관적 락은 보완해 사용한다. 메시지는 중복 전달될 수 있지만 정산의 자금 반영은 한 번이어야 한다.

진행 순서: `1·2 긴급 보완 -> 3·5·6 모델·정책 확정 -> 4 공통 정산 구현 -> 7 전달 구조·병렬화 -> 8 운영 검증`. 각 단계에서 테스트하고 커밋한다. MySQL·Redis 장애 테스트는 마지막에 몰아서 하지 않는다.

상태: 2026-10-13 코드 검토 기준 개선 계획이다. **아래 목표 구조의 구현·효과는 미검증**이다. 후속 구현자는 실제 코드·DB 스키마를 재확인하고, 정책 변경은 구현 전에 이 문서에 명시한다. 기대 효과를 완료 실적으로 표시하지 않는다.

## 1. 일반 입출금 검증과 계좌 접근 통제 [최우선]

- **현재 문제:** 일반 입출금은 양수 금액 검증과 잠금 없이 잔액을 직접 변경한다. 계좌 생성 API는 비인증 접근을 허용하며 요청 userId와 초기 잔액 10억 원을 사용한다.
- **개선·근거:** 금액·허용 소수 자릿수·통화·계좌 상태·소유권을 검사하고 모든 자금 변경에 공통 잠금·예약 규칙을 적용한다. 사용자 식별은 인증 주체를 기준으로 한다. 계좌 생성은 권한을 확인하고 테스트 자금은 개발용 seed로 격리한다. 환전 경로만 보호하면 일반 출금을 통한 정합성 훼손이 남는다.
- **결과 검증:** 음수 입출금과 무권한 계좌 생성을 거절하고, 환전·출금 동시 실행에서도 갱신 유실과 음수 가용 잔액이 없어야 한다.
- **코드 근거:** [WalletServiceImpl](../backend/src/main/kotlin/org/example/backend/user/service/WalletServiceImpl.kt), [SecurityConfig](../backend/src/main/kotlin/org/example/backend/common/config/SecurityConfig.kt), [AccountServiceImpl](../backend/src/main/kotlin/org/example/backend/user/service/AccountServiceImpl.kt).

## 2. Worker 실패 처리와 중복 실행 방지 [최우선]

- **현재 문제:** ACK 오류를 정산 실패로 취급한다. 최종 재시도에서는 메시지 제거 후 DB에 실패를 기록하므로 중간 장애 시 주문이 미완료로 남을 수 있다. lease 복구에는 소유권 경합 위험도 있다.
- **개선·근거:** 정산과 ACK 예외를 분리한다. 업무상 거절은 재시도하지 않고, 교착·일시 장애는 전체 트랜잭션을 지연 재시도한다. 재시도 횟수·다음 실행 시각·오류 분류를 DB에 저장하고 상한 초과는 격리·운영 확인 대상으로 관리한다. 기존 List 유지 중에는 claim 소유권 확인과 인계를 원자화한다.
- **실패 확정:** ACK 실패는 재정산 실패가 아니다. DB 커밋 응답이 끊기면 주문·전표를 조회해 결과를 확인한다. 결과 불명인 동안 예약을 유지하며, 미정산이 확인된 최종 실패만 `실패 + 예약 해제` 커밋 후 ACK한다. 오래된 Worker가 실패를 덮어쓰지 못하도록 DB 종료 상태·시도 버전을 검사한다.
- **멱등성:** 기존 `(userId, idempotencyKey)` 유니크 제약을 유지하고 키 필수화 전환을 준비한다. 정규화한 요청 내용·견적을 비교해 동일 키·다른 내용은 거절한다. 동일 요청은 기존 주문을 반환하고 응답 유실 시 조회할 API를 제공한다. 재전달은 주문 잠금·종료 상태와 정산 전표 유니크 제약으로 보호하며 Redis 키 만료에 의존하지 않는다.
- **결과 검증:** 커밋 전후 Worker 종료, ACK 실패, 실패 기록 저장 실패, 중복 전달에도 자금은 한 번만 반영되고 접수 주문을 추적·복구할 수 있어야 한다.
- **코드 근거:** [OrderWorker](../backend/src/main/kotlin/org/example/backend/exchange/service/OrderWorker.kt), [RedisOrderQueue](../backend/src/main/kotlin/org/example/backend/common/util/RedisOrderQueue.kt).

## 3. 지갑·외부 계좌·회계계정 구분

- **현재 문제:** Account가 사용자 연결계좌와 회사 계좌 역할을 함께 담당한다. Wallet에는 연결 상태가 중복 표현되며, 잔액 정밀도와 사용자·통화 유니크 제약은 실제 DB 확인이 필요하다.
- **개선·근거:** 지갑은 고객의 통화별 잔액, 연결계좌는 외부 은행 참조, 내부 회계계정은 고객 채무·회사 자산·수수료 등의 기장 단위로 구분한다. 금액은 BigDecimal·명시적 DECIMAL 정밀도를 사용하고 `(userId, currencyId)` 유니크 제약을 둔다. 외부 은행 잔액을 로컬 값 변경만으로 실제 이체했다고 취급하지 않는다.
- **결과 검증:** 입금·환전·출금의 회사 자산과 고객 지갑 변동을 설명할 수 있어야 한다. 지갑을 회사의 고객 채무로 정의하면 입금 시 회사 예금 자산과 고객 지갑 채무가 함께 증가하며, 이는 자금 중복 지급이 아니다.
- **코드 근거:** [Wallet](../backend/src/main/kotlin/org/example/backend/user/domain/Wallet.kt), [Account](../backend/src/main/kotlin/org/example/backend/user/domain/Account.kt).

## 4. 정산 실행기와 잠금 규칙 통합

- **현재 문제:** BUY·SELL에서 이체 호출을 나열하고 개별 이체마다 출금 측부터 잠근다. 반대 방향 거래 간 잠금 순서가 충돌할 수 있으며 접수 검증을 우회하는 즉시 처리 경로도 있다.
- **개선·근거:** 견적·금액·수수료로 불변 PostingPlan을 만들고 PostingService가 검증·기장한다. 독립 주문은 접수 경로로만 받고 차익거래 내부 실행도 공통 정산 실행기를 사용한다. 공통 잠금 순서는 `사용자 ID순 -> 주문 ID순 -> 일일 한도 -> 예약 -> 전체 잔액 행(자원 종류·ID순)`으로 정하고, 입출금·취소·복구도 따른다. 현재의 주문 우선 잠금 경로도 함께 바꾼다.
- **잠금 경계:** 정산에 필요한 모든 잔액 행을 먼저 잠근 뒤 최신 잔액·예약을 검증한다. 락을 잡은 채 Redis·은행 API를 호출하거나 재시도를 대기하지 않는다. 교착·락 타임아웃은 트랜잭션 종료 후 새 트랜잭션에서 전체 재시도한다. Spring 프록시를 통과하는 서비스 경계로 롤백을 검증한다. [MySQL 근거](https://dev.mysql.com/doc/refman/8.0/en/innodb-deadlocks.html).
- **원자적 범위:** 잔액, 전표, 체결 원본, 예약 사용, 주문 완료, 완료 Outbox를 한 DB 트랜잭션으로 저장한다. 주문 내부의 출금·입금을 병렬화하지 않는다. 차익거래는 부모·하위 실행을 구분해 예약과 한도를 중복 적용하지 않는다.
- **결과 검증:** 어떤 중간 단계에서 예외가 나도 정산 변경이 모두 롤백되어야 한다. 공통 계산 결과만 공유하고 주문·체결·전표 DTO는 책임별로 유지한다.
- **코드 근거:** [ExchangeOrderServiceImpl](../backend/src/main/kotlin/org/example/backend/exchange/service/ExchangeOrderServiceImpl.kt), [MoneyMovementServiceImpl](../backend/src/main/kotlin/org/example/backend/user/service/MoneyMovementServiceImpl.kt).

## 5. 접수 시 자금·한도 예약과 견적 확정

- **현재 문제:** 활성 주문 합산으로 예약액을 계산하지만 일반 출금이 이를 준수하지 않는다. 사용자 동의 견적이 저장되지 않으며, `unit`을 고시 단위와 최소 주문 기준으로 함께 사용한다. 최소 구매액에서도 수수료 차감 후 수령량은 고시 단위보다 작을 수 있다.
- **개선·근거:** 접수 트랜잭션에서 주문·자금 예약·일일 한도 예약·Outbox를 함께 저장한다. 주문별 예약 상태는 `HELD -> CONSUMED / RELEASED`로 한 번만 전환한다. 일반 출금은 `잔액 - 전체 예약액`, 정산은 해당 주문의 예약 권리를 검사한다. 자기 예약을 다시 가용 잔액에서 차감해 거절하지 않는다. 항상 `0 <= 예약액 <= 잔액`을 유지한다.
- **한도:** `(userId, 업무일)` 유니크 행을 생성·잠금한 뒤 `사용액 + 예약액 + 신규 요청액 <= 4,000 USD`를 검사한다. 초기안은 서울 기준 접수 업무일과 USD 환산액·환산 근거를 저장해 고정하고, 자정 이후 완료·해제도 해당 업무일에 반영한다. 현재처럼 수수료 포함 출금액을 환산하고 차익거래는 부모 주문에서 한 번 계산한다. 4,000 USD는 프로젝트 정책이다.
- **견적·단위:** 서버 견적에 quoteId·환율 종류/고시 시각·unit·수수료 정책·예상/최소 수령액·만료 시각을 남긴다. 고시 단위와 최소 주문 정책은 구분하되 초기 최소값은 기존 unit 기준을 유지한다. 수수료 후 최소 실수령 보장 여부, 견적 유효시간·허용 변동은 구현 전 확정한다. 화면과 서버가 같은 정책을 사용한다.
- **상태 정책:** 공개 상태는 접수·처리 중·완료·취소·실패로 단순화하고 재시도·복구 메타데이터는 내부 관리한다. 접수 전 잔액·한도 거절은 주문 이력에 남기지 않는다. 견적 위반은 취소 사유(RATE_CHANGED 등)를 표시하고 예약을 해제한다. 기타 최종 실패는 일반화하고 내부 원인은 감사 기록에 남긴다. 상태 축약과 별개로 주문 조회 소유권을 검사한다.
- **결과 검증:** 동시 주문·일반 출금·자정 경계에서도 잔액과 한도를 지키고, 완료·취소·실패 재처리 시 예약이 한 번만 사용 또는 해제되어야 한다.
- **코드 근거:** [현재 검증 코드](../backend/src/main/kotlin/org/example/backend/exchange/service/ExchangeOrderRequestValidator.kt).

## 6. 전표·분개와 대사 도입

- **현재 문제:** 장부가 환전 요약 중심이어서 주문별 계정 증감과 현재 잔액을 충분히 대사하기 어렵다.
- **개선·근거:** 주문에 연결된 전표와 계정·통화별 차대 분개를 저장한다. 환전 중계 계정을 포함한 기장 예시를 BUY·SELL·수수료·입출금별로 먼저 정의하고 통화별 차변·대변 합계를 검증한다. KRW와 USD 금액을 직접 합산해 균형을 맞추지 않는다. 정산 ID는 `(orderId, 실행 단계)`마다 고정하며 재시도마다 새로 만들지 않는다. `(정산 ID, 전표 종류)` 유니크 제약과 원전표를 참조하는 역분개를 사용한다. 원장은 변경 근거, 잔액은 같은 트랜잭션에서 유지되는 운영 집계값이다.
- **결과 검증:** 기초 잔액과 분개로 기말 잔액을 설명하고, 성공 주문의 전표 누락·중복·예약 잔류를 배치로 탐지해야 한다. 주문 하나에 분개가 여러 행이므로 단순 행 수 동일 비교는 하지 않는다.
- **코드 근거:** [ExchangeLedger](../backend/src/main/kotlin/org/example/backend/exchange/domain/ExchangeLedger.kt).

## 7. 정산 큐와 후처리 분리

- **현재 문제:** 직접 구현한 List·lease 복구 구조이며 Outbox는 접수 이벤트 중심이다. 큐 수를 늘리는 것만으로 순서·유실·중복 문제가 해결되지는 않는다.
- **개선·근거:** DB 정산 안전성 확보 후 Redis Streams의 pending·인계·ACK로 전환한다. 인계는 기존 Worker 실행을 중지시키지 않으므로 DB 중복 방어를 유지한다. 발행 완료는 업무 완료가 아니며 Redis 전체 유실에도 DB 미완료 주문을 재발행한다. 기존 Redis 발행 중복키가 복구 재발행을 막지 않게 설계한다. [Redis 근거](https://redis.io/docs/latest/commands/xautoclaim/).
- **Outbox:** `짧은 DB claim -> DB 트랜잭션 밖에서 발행 -> claim 소유권 조건으로 발행 결과 저장`과 만료 claim 복구를 구현한다. 발행 후 상태 저장 실패에 따른 중복을 허용하고, 후처리 소비자는 eventId 처리이력과 주문 버전으로 중복·역순을 방어한다. [Outbox 근거](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html).
- **분리 범위:** 정산·Outbox 발행·복구·후처리의 실행 자원과 배치 상한을 분리한다. 자금·전표·체결 원본은 동기 저장하고 재생성 가능한 조회 데이터·알림·통계만 완료 이벤트로 처리한다. 각 기능이 모든 이벤트를 받아야 하면 별도 consumer group으로 구독한다.
- **순서 정책:** 초기안은 사용자별 DB 접수 순번을 사용자 잠금 아래 부여하고, 선행 주문 종료 전에는 잠금을 풀고 후속 주문을 재스케줄한다. 이 대기는 장애 재시도 횟수에 포함하지 않는다. API 도착 시각·초 단위 묶음·락 획득 순서를 FIFO로 간주하지 않으며, 다른 사용자 간 전역 순서는 요구하지 않는다. 단일 Worker 검증 후 다중 Worker로 확대하고 공용 회사 계좌의 락 대기·처리량을 측정한다.
- **결과 검증:** 후처리 장애가 정산 완료를 되돌리지 않고, 중복·역순 이벤트에도 조회 결과가 일치해야 한다. 미완료 주문 나이·Outbox 지연·락 대기를 측정한다. [Outbox 코드](../backend/src/main/kotlin/org/example/backend/exchange/service/OutboxEventPublisher.kt).

## 8. 외부 연계와 실제 결과 검증

- **현재 한계:** H2·mock 테스트만으로 실제 MySQL 잠금과 Redis 장애 복구를 입증할 수 없다. 현재 모의 은행 잔액 처리는 실제 은행 연동과 구분해야 한다.
- **개선·근거:** 실제 MySQL·Redis 통합 테스트와 모의 은행을 사용한다. 은행 요청 ID, 결과 조회, 대사를 구현해 은행 성공 후 응답 타임아웃을 재현한다. 외부 결과 불명은 바로 실패 확정하거나 예약 해제하지 않는다.
- **필수 검증:** 단계별 롤백, 환전·일반 출금 경합, 동일·서로 다른 사용자 동시 요청, 반대 방향 이체, 중복 요청, 커밋 직후 Worker 종료, 오래된 Worker 재개, Redis 전체 유실, 한도·JPY 단위·반올림 경계, 대사 재실행. 결과는 잔액·예약·전표·주문 상태를 함께 비교한다. 수동 재처리는 권한·사유·결과를 감사 기록으로 남긴다.
- **배포 기준:** 스키마를 단계적으로 추가하고 기존 활성 주문·예약·큐를 대사 후 전환한다. 과거 요약으로 상세 분개를 임의 복원하지 않는다. 기존 주문 소진과 롤백 절차를 검증한다.
- **실제 결과 기록:** 각 항목 완료 시 `커밋 / 테스트 명령·환경 / 통과·실패 / 남은 한계`를 한 줄로 추가한다. 병렬화 전후에는 같은 부하의 처리량·p95 지연·락 대기·복구 시간을 비교한다. 현재 목표 구조의 검증·성능 수치는 없다.

## 9. 최종 처리 흐름

```text
주문 API: 동일 요청에는 동일 idempotencyKey
  -> [접수 DB 트랜잭션]
     공통 잠금 -> 중복·견적·잔액·한도 검증
     -> 사용자별 접수 순번 + 주문 + 자금·한도 예약 + 접수 Outbox
  -> COMMIT 후 "접수됨" 응답 (환전 완료 아님)
  -> Outbox 발행 -> 정산 큐 -> Worker
  -> [정산 DB 트랜잭션]
     공통 순서로 잠금 -> 종료 상태·처리 순서·견적·예약 검증
     -> 잔액 반영 + 전표·체결 원본 + 예약 사용
     -> 주문 완료 + 완료 Outbox
  -> COMMIT -> ACK
  -> 완료 이벤트 -> 조회 데이터·알림·통계 후처리

견적 정책 위반: 정산 없이 취소·사유·예약 해제·종료 Outbox 커밋 -> ACK
일시 정산 예외: 전체 롤백 -> 별도 DB 트랜잭션에 재시도 계획 저장
  -> ACK (DB 스케줄러가 재발행, 저장 실패 시 ACK하지 않음)
최종 실패: 미정산·종료 상태·시도 버전 재확인
  -> 실패·예약 해제·종료 Outbox 커밋 -> ACK
ACK 실패: 재전달 -> 종료 상태 확인 -> ACK (자금 재반영 없음)
커밋 결과 불명: DB 결과 확인 전까지 실패 확정·예약 해제 보류
장기 미완료: DB 기준 탐지 -> 재발행 또는 운영 확인 (예약 자동 해제 금지)
```

이 흐름은 내부 DB 정산 기준이다. 외부 은행 결제가 포함되면 요청·결과 확인·대사를 별도 단계로 두고 고객에게 약속하는 완료 시점을 정의한다. 외부 송금은 DB 롤백으로 되돌릴 수 없다.
